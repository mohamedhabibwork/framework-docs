Release classification required by [`framwork.md`](https://github.com/mohamedhabibwork/framework/blob/main/framwork.md) §10.

- **Validated** — covered by an automated test that runs in `bun run test`.
- **Implemented** — works and is exercised, but without a dedicated automated test.
- **Contracts** — published types and DI tokens only; no runtime yet.
- **Planned** — specified but not built (the CLI lists it and exits with code 3).

This page is a claim sheet, so every row names its evidence. The numbers are
deliberately absent: test counts drift with every commit, and the suite is the
source of truth — `bun run test`, `bun run coverage`, `bun run typecheck`,
`bun run lint`. Last structural review: 2026-10-28.

## Kit-backed subsystems

All five `@mohamedhabibwork` kits are adapted behind framework contracts (ADR-11)
and wired through the whole stack: the playground binds `cache` / `logging` /
`storage` providers and implements the CLI runtime hooks (`cache`, `sessions`),
so `cache:clear`, `storage:check` and `session:prune` execute for real. Generated
applications ship the same providers, config sections (env-mapped) and hooks from
`create`, with the sessions hook tolerating apps that have not run `make:auth`
yet. Notifications gains push (fcm/apns/webpush/huawei) and messaging
(telegram/slack) channels over NotifyKit with per-channel provider config; email
stays on `@framework/mail` by design.

Gate evidence: `packages/cli/tests/create-app.test.ts` (kit assertions in the
generated-app gate), `packages/cli/tests/cli.test.ts` (provider gates and
playground end-to-end), `packages/notifications/tests/notifications-kit.test.ts`.

## Generated application (`create`)

`bun run cli -- create apps/<name>` generates the application skeleton the
release gate exercises: validated config (app/http/database/redis/queue/events),
database and events providers, `audit_logs` in the canonical schema, `/health`,
`/audit` and `/ws` routes, `bin/server.ts` + `bin/worker.ts` + `bin/scheduler.ts`

- `bin/cli.ts` entry points, a health smoke suite, deployment compose, drizzle
  config and a README. `make:crud --verify` then adds a full resource module.
  Generated apps are workspace members: dependencies resolve through `workspace:*`
  after a root `bun install` (run by `create` unless `--no-install`).

## Documentation site

`apps/docs` is a static Starlight build (`output: 'static'`) served by nginx from
the Dokploy image (`apps/docs/Dockerfile`), with TLS terminated upstream. The
guides are generated from [`docs/`](https://github.com/mohamedhabibwork/framework/blob/main/README.md) by `bun run docs:sync`, and
`bun run docs:check` fails the build on drift, missing frontmatter, orphan pages
or broken internal links. Versioned lines archive to their own Starlight locale
(`v01/`), written only by the release script.

## Known limitations

- Generated CRUD supports a single primary key named `id` (uuid for new tables; uuid/integer/serial for existing tables). Unique/foreign-key fixtures, relations, enums and JSON columns are rejected rather than guessed.
- Generated resources support `--access public` and (after `make:auth`) `--access authenticated`; per-principal ownership is available as a service-level `ownedBy('userId')` scope but is not a `make:crud` flag, and the `?include=` relations DSL is not generated.
- Import/export covers CSV and JSON (streaming keyset batches, queued, partial-success imports). XLSX/PDF are planned. Export artifacts can live on any storage disk (`DiskExportStore`) or local disk (`LocalExportStore`).
- TOTP two-step login provisions the RFC 6238 §5 SHA-256 variant only (`algorithm=SHA256`); authenticator apps without SHA-256 support (notably Google Authenticator) cannot enroll — Aegis, 1Password, Bitwarden, FreeOTP and Ente Auth work. Documented in `packages/auth/src/totp.ts`.
- TOTP secrets are stored in the `users` table unencrypted (they must be retrievable to verify codes); database-at-rest encryption is a deployment concern.
- Node is not a selectable runtime; only Bun is validated (the generated Dockerfile pins `oven/bun:1.4.2`). The docs site itself needs Node ≥ 22.23.4 to build.
- Batch bookkeeping (queue batches) lives in Redis with a TTL, so batch history is bounded by design; durable fan-out with history belongs in workflows.
- OpenTelemetry tracing/metrics and the "every CLI command has a status row" CI check are planned (M7 remainder). Per-status OpenAPI error schemas ship today, and `bun run coverage` enforces per-package line/function thresholds.
- SMTP transport, the SMS notification channel, and validated s3/r2/minio storage against MinIO in compose are planned (M6 remainder).
- `@framework/search` supports `memory` and `postgres` only; typo tolerance, facets and external engines are not implemented. `@framework/observatory` and `@framework/socialite` are contracts only.
- Migrations are forward-only by decision: `db:rollback` stays planned, with a pointer to `db:fresh` (non-production) and authoring a new forward migration.
- The docs site vendors MDX 8's wasm32 runtime (`apps/docs/vendor/`, installed by a postinstall script) because Bun skips wasm32 optional dependencies; the Docker build uses a glibc base so the native binding loads.
